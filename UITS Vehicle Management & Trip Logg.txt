UITS Vehicle Management & Trip Logging System

1. Project Overview

Build a secure, responsive, web-based internal application for the University Information Technology Services (UITS) to manage and monitor the use of its official vehicles.

UITS currently has:

- 2 pickup vehicles
- 2 designated drivers
- Staff who request vehicles for official duties
- Designated officers who approve vehicle requests

The system must provide a complete lifecycle for each vehicle request:

Request → Approval → Vehicle/Driver Assignment → Trip Start → Trip Completion → Reporting → Analytics

The system must maintain an auditable history of all vehicle usage.

The application is intended for internal institutional use and should be simple enough for staff and drivers to use from computers and mobile phones.

7. Request Validation

The system must validate:

- Destination cannot be empty
- Purpose cannot be empty
- Date cannot be invalid
- Number of passengers must be greater than zero
- Requested departure must precede expected return
- Requests cannot be submitted for dates that are already invalid/past unless an administrator explicitly permits this
- Passenger capacity should not exceed the configured vehicle capacity

Display clear validation messages.

13. Starting a Trip

When the vehicle actually leaves, the Transport/Admin Officer or authorised driver selects:

START TRIP

The system records:

- Actual start timestamp automatically
- Starting odometer
- User who started the trip

The user should not manually enter the start time.

Once started:

SCHEDULED → IN_PROGRESS

The vehicle status becomes:

ON_TRIP

The driver becomes:

ON_TRIP

---

14. Ending a Trip

When the vehicle returns:

Select:

END TRIP

Require:

- Ending odometer
- Trip completion remarks where necessary

Automatically calculate:

Distance = Ending Odometer - Starting Odometer

Automatically record:

- Actual end timestamp
- User who ended the trip
- Trip duration

Trip status becomes:

COMPLETED

Vehicle becomes:

AVAILABLE

Driver becomes:

AVAILABLE

---

15. Odometer Validation

The system must ensure:

Ending Odometer >= Starting Odometer

Also ensure the new vehicle odometer is not lower than the vehicle's previously recorded odometer.

Administrators can correct erroneous readings, but every correction must be recorded in the audit log.

- Input validation

---

32. Data Integrity

The backend must prevent:

- Double booking vehicles
- Double booking drivers
- Starting a trip that is already completed
- Completing a trip that has not started
- Negative trip distances
- Invalid odometer readings
- Unauthorized modification of completed trips
- Approval by unauthorized users

Use database transactions for critical operations.

---

33. Concurrency

Vehicle assignment and trip starting must be protected against race conditions.

For example:

Two administrators should not be able to simultaneously assign UITS-01 to two overlapping trips.

Use database transactions and appropriate locking/validation.

---

34. Search and Filtering

All major tables should support:

- Search
- Pagination
- Sorting
- Date filtering
- Status filtering

The backend should perform filtering and pagination rather than loading thousands of records into the browser.
